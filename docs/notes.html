2. The story in one page

You had been training for seven or eight months, found muscle gain easy and fat loss hard in a carb-rich Indian household, and started logging dinner into a ChatGPT project each night to get calories, macros and the deficit. It sometimes hallucinated. The idea was a simple app where a meal typed in plain language is worked out by a hybrid: an AI for understanding the sentence, and a real food database for the numbers, each checking the other, so the daily dashboard updates every time you eat.

That idea is still the north star, and it is now the private engine at the centre of a larger product called Grain:

  • Describe, don't scan. A photo cannot see the ghee in the pan or the chicken under the rice. People who already know what they ate type or say it.
  • Grounded numbers. Every food number comes from a measured source (a curated Indian dish table, India's lab-measured IFCT 2017, or USDA FoodData Central) or is visibly flagged as an estimate.
  • Arithmetic in code. The model picks foods; code multiplies portions. A cross-check cannot catch a mistake both sides make, so weights never go through the model's maths.
  • Honest history. Days nobody logged count as nothing, never as a deficit. A half-logged day is held out until finished.
  • An ecosystem for people who train. Food, training with every set, programs and meal plans, imports of old history and a coach's view, all on one timeline. The engine is the moat; everything else is a service around it.
  • Audience. Athletes, lifters, models and fitness creators, India first and now global. They weigh their food, notice a wrong number, and pay for tools that get it right.

Names: the project started as Deficit (you still see deficit in folder names and storage keys) and became Grain, a name about precision rather than dieting. The domain is getgrain.fit; the app is at app.getgrain.fit.

3. The big picture: who talks to whom

Three things to hold in your head:

  1. The app is a static website. Vercel only hands out files. All the "thinking" happens either inside the phone's browser (the maths, the training logger, the offline parser) or inside Supabase (the engine).
  2. The phone talks to Supabase directly for data. There is no separate Grain API server. The app reads and writes its own rows in Postgres using the public anon key, and RLS keeps everyone in their own lane.
  3. Only the Edge Function talks to Groq and USDA. That is why the keys stay secret and why the engine can be upgraded without shipping a new app.

5. The app shell: screens, gates and the installable web app

5.1 What happens when the app opens

  • AuthProvider asks Supabase whether a session exists (sessions persist in the browser's localStorage). While it asks, a spinner shows. When a session arrives it points the storage facade at the cloud (chapter 6).
  • AuthGate shows the sign in screen when accounts are switched on and nobody is signed in. If the two EXPO_PUBLIC_SUPABASE_* variables are missing, the app runs entirely on the device with no account at all.
  • ConsentGate runs once per account and per consent version. If the device already remembers that this version was agreed, it costs nothing. Otherwise it asks the database, and any doubt (offline, error) is treated as "not yet agreed", because asking again is harmless.
  • AppTabs is the tab bar. On Overview, if there is no saved profile, the onboarding questionnaire takes over the screen.

5.2 Onboarding

Seven questions, one per screen: biological sex, age, height, weight, activity level, desired loss rate, and a review that shows the computed target live before the user has finished (the "aha" lands early). Ages under 18 are refused. Each option explains itself in a short hint ("Hard exercise 6 to 7 days a week"). The result is a ProfileInput saved under the profile key; nothing else is stored from onboarding.

5.4 The installable app: manifest, service worker, install button

Manifest. public/manifest.json names the app ("Grain"), sets it to open full screen (display: standalone), and lists the icons. The icon URLs carry ?v=2 because installed phones kept the old logo when the files were replaced under the same name.

Service worker. A small script the browser keeps running in the background so the app can open offline. Its rules are deliberately narrow:

  • Anything not on the app's own domain (Supabase auth, database, Edge Function) is never touched. It goes straight to the network.
  • Build files with a content hash in their name (/_expo/static/, /assets/) are served cache first, because a changed file always gets a new name.
  • Everything else, above all the HTML page that names the current bundle, is network first with the cache as a fallback. So a new deploy is picked up on the next load.
The bug that deleted mealsThe first service worker cached every request, including database reads. The app stores a whole day as one JSON list and saves by read, modify, write. A stale cached read of today, plus a fresh write, saved the day with the newest meals missing. They were not hidden, they were gone. Lesson written into the code: offline caching and read-modify-write storage do not mix, so API traffic is never cached. The cache name was bumped to grain-v3 to evict old copies on every phone.

Install button. Chrome offers "install this app" exactly once, early, via an event named beforeinstallprompt. The button lived on Profile, which mounts much later, so the offer was always missed. Fix: a tiny inline script in the HTML head catches the event before the 2.3 MB bundle even parses, stashes it on window, and install-prompt.ts hands it to the button when it appears. A prompt can be used once, so after "dismissed" the UI falls back to manual instructions.

Look. Light only, "warm instrument": bone background, warm ink, one orange accent. No dashes or minus signs anywhere in copy; the label carries the direction ("Down 1.2 kg"). Figures use tabular numerals so columns line up.

6. Where data lives: the key/value idea

This is the most important architectural decision in the app, and the one that makes everything else simple. Grain does not have a "meals table", a "weights table" and a "workouts table" in the database. It has one storage interface with three methods and everything is a JSON string under a named key.

interface KVStore {
  get(key): Promise<string | null>;
  set(key, value): Promise<void>;
  remove(key): Promise<void>;
}

Picture a coat check with named hooks. The profile hangs on the hook "deficit.profile.v1". Today's meals hang on "deficit.log.v1.2026-11-12". The app never cares whether the coat room is in the phone or in the cloud.

6.1 Sign in moves the facade, and migrates once

When a session appears, auth.tsx calls setActiveStore(cloud). Then migrateLocalToCloud runs: if the cloud has no profile for this user yet, every deficit.* key in the phone's localStorage is pushed up. So someone who used Grain without an account keeps their data when they sign in. It runs once per device and is best effort; it never blocks sign in. On sign out the facade points back to the device.

6.2 Device-only keys are named per account

Some things must stay on the phone (offline copies, the outbox, cached consent). They are named grain.<accountId>.<name> via deviceKey(). That way two people signing in on one phone never see or sync each other's training. Deleting an account also clears that account's device keys.

6.3 The daily log, and why writes are queued

One key per calendar day, in the phone's local date (todayKey() uses local year, month and day, not UTC, so a meal at 11 pm in Mumbai lands on the right day). Each entry stores:

FieldMeaning
id, label, atA short random id, the food's name, and when it was logged.
kcal, proteinG, carbsG, fatGTotals for this entry (unit × quantity).
serving, quantityThe serving the unit macros describe ("1 katori (150g)" or "100g") and how many of it. Editable later.
unitKcal, unitProteinG, unitCarbsG, unitFatGPer-serving macros, kept so quantity can be rescaled without going back to the engine.
confidence, sourceThe engine's trust signal at log time (high, medium, low) and where the number came from (local, usda, ifct, ai). This follows the entry into the log so a guess is never hidden.
The mutation queueAdd, remove and change-quantity each read the day, change it, and write it back. If two of these overlap (a multi-item meal logs several entries at once, or a double tap), the second read could see the old list and its write would drop the first entry. log-store.ts therefore chains every operation on the same day key behind the previous one (serialized()), and even reads go through the queue, because the Log screen reloads on every focus and a stale read once made a meal vanish from the list while it was still in storage.
7 grams became 50 gramsQuantities used to be floored at half a serving. For a food measured "per 100 g", half a serving is 50 g, so half a tablespoon of sugar (7 g, 27 kcal in the composer) was saved as 50 g and 193 kcal. Now the quantity is saved exactly as given; the stepper moves weighed foods in 5 g steps and countable foods in halves (quantity.ts), and "minus" at the bottom of the grid does nothing rather than jumping to a floor.

6.4 Workouts are stored per month

Finished workouts live under deficit.workouts.v1.YYYY-MM with an index of months under deficit.workouts.months.v1, so saving a workout never rewrites years of history. Chapter 15 covers the offline outbox that sits in front of this.

6.5 Trade-offs of this design, stated plainly

  • Good: one table, one security policy, trivially testable, no schema migrations for new features, offline mode and cloud mode share all code.
  • Cost: the database cannot query inside the JSON cheaply. Admin stats parse each day's JSON with a helper SQL function (log_entry_count). Reading many days is batched: the store has an optional getMany, and the account store answers it with one request per hundred keys, so the Overview's 45 days, a month on the calendar or a year of History each cost one or a few round trips instead of one per day.

7. Sign in and accounts

  • Google only. The email magic link was removed on 22 October 2026: one path, nothing to deliver to an inbox, nothing to land in spam, and no SMTP to set up.
  • Implicit flow, on purpose. Supabase supports two OAuth flows. PKCE stores a secret in the browser that started the sign in and expects the same browser to finish it; links opened in another browser or an in-app webview silently bounce back to the login screen. Implicit carries the session in the redirect itself, so it completes wherever it opens. Do not switch to PKCE without a verifier-free path.
  • Where the session lives. In the browser's localStorage, refreshed automatically by the Supabase client.
  • Program links before sign in. If someone opens app.getgrain.fit/program?code=ABC123 while signed out, the code is remembered, Google sign in lands on Home, and Home opens the program.
  • Privacy copy. The sign in screen and Profile say that meals are saved without your name to make estimates better (chapter 9.9 explains the salted hash).

9. The food engine, stage by stage

9.1 Is it RAG?

Yes in spirit, no in mechanism. Classic RAG turns documents into vectors (lists of numbers) and finds the closest ones to the question. Grain's engine instead retrieves candidate foods by name matching from three tables, hands those candidates to the model, and lets the model choose. Then code does the arithmetic. Call it grounded parsing with a judge. The reason for the simpler retrieval: food names are short, the tables are small (about 1,100 curated and IFCT rows compiled into the function, plus USDA over the network), and name matching is explainable: you can always see why a candidate appeared. The engine review in the lab notes this search is also the weakest link (it once offered "Betel leaves, big" for a Big Mac), and a proper food search with weights per household measure is on the roadmap.

9.2 A worked example

Input: "200g chicken breast, 1 katori dal tadka, 1 tablespoon ghee".

  1. Structure returns three items: chicken breast (quantity 1, query "cooked chicken breast", grams 200), dal tadka (quantity 1, query "cooked lentils dal", grams null), ghee (quantity 1, query "ghee clarified butter", grams 14).
  2. Look up. Chicken: the curated table has nothing exact, IFCT offers "Chicken, breast" raw at 100 g raw, USDA offers "Chicken, breast, cooked" per 100 g. Dal: the curated table offers "Dal Tadka, 1 katori (150g)", IFCT offers red gram cooked and raw. Ghee: curated "Ghee, 1 tsp (5g)" and USDA "Butter oil, anhydrous" per 100 g.
  3. Judge picks USDA cooked chicken (the user said 200 g of something cooked), the curated Dal Tadka with quantity 1, and USDA ghee. It estimates 330, 180 and 125 kcal independently.
  4. Calculate. Chicken: per 100 g and 200 g stated, so multiplier 2.0 (165 × 2 = 330). Dal: countable serving, quantity 1 (180). Ghee: per 100 g, 14 g stated, multiplier 0.14 (876 × 0.14 = 123). Before this rule existed, this ghee logged as 876 kcal with a "high" badge, because the model's cross-check made the same mistake.
  5. Flag. All three gaps are small and portions are clear, so all three are "high". Total 633 kcal.

9.3 The confidence rule, exactly

function calcConfidence(dbTotal, aiKcal, portionCertainty, source) {
  if (!aiKcal) return 'low';            // no cross-check at all = a guess
  gap = |dbTotal - aiKcal| / max(aiKcal, dbTotal, 1);
  tol = source === 'local' ? 0.25 : 0.20; // home recipes vary more
  if (portionCertainty === 'clear' && gap <= tol) return 'high';
  if (gap <= 0.40) return 'medium';
  return 'low';
}

In words: high means the database and the model agree within 20% (25% for home dishes) and the portion was clear. medium means they are within 40% or the portion was guessed. low means they really disagree, or there was no cross-check, or no database match at all (the model's own estimate is always low). The app shows these as Matched, Likely, Unsure. The reason line for anything below high says it plainly: "Database says 180 kcal, AI estimate about 260 kcal, recipes vary."

An honest limitationConfidence is the model agreeing with the database, and nobody has yet measured how often "high" is actually right. That measurement is what the practice set in the lab is for (chapter 24).

9.4 Degraded runs

A run is degraded when infrastructure or the judge failed: USDA was unreachable (distinct from "USDA answered and had nothing"), the model returned no decision for an item, or an item could not be placed at all. A degraded run still answers (logging must never hard-fail), shows a note ("Grounding was incomplete for this meal... try again in a minute"), and is never cached. An honest low-confidence result is not degraded and is cached, because it is reproducible and already flagged.

Why the engine once looked randomRuns made while USDA was down were being cached for a week, shared across all users. The same meal typed again returned the same wrong calories for seven days, while a phrase first parsed when USDA was healthy stayed right. That is what made the engine look "sometimes right, sometimes wildly off". Caching only fully grounded runs fixed it.

9.5 The cache

Key: v5 | model name | lower-cased, whitespace-collapsed text. So "200g chicken" and "200G chicken" share an answer, switching models starts a fresh namespace, and bumping ENGINE_VERSION (now v5) after any change to the output retires every old answer. Hits are served in well under a second and still produce a run row marked cached. The cache is written after the reply has gone, so it never adds to the wait.

USDA answers are remembered too (caches.ts). A USDA search takes about 2 seconds from India, and the same foods come up constantly ("cooked white rice", "chicken breast cooked"), even when the whole meal text is new. Each answer is kept in the instance's memory and in food_cache under usda|v1| plus a hash of the exact query, for 30 days, because USDA's data barely changes. On a meal, memory is checked first; for the rest, the stored answers and USDA are asked at the same time and a stored answer cancels its USDA search. So a known food costs nothing or one database read, and a new one waits no longer than before. "USDA unavailable" is never remembered, a search that hangs past 8 seconds counts as unavailable (a degraded run), and the answers are byte for byte the ones USDA gave.

9.6 The two prompts

Structure prompt (paraphrased): "You are a nutrition assistant for Indian food. Break this meal into items. For each return a display name, quantity as a decimal, a concise generic English search query ('cooked lentils dal', 'wheat flatbread roti'), and grams: the edible weight of the whole eaten amount, only when a measurable amount is stated. Normalise Indian portions. Return only JSON."

Judge prompt (paraphrased): "You are grounding a food log so its numbers can be trusted. For each item you get real candidates from three sources... Choose the best; prefer a specific Indian table match over a generic USDA one; if none fits use -1 and give your own estimate with a serving label. Raw vs as-eaten rules. Return quantity in the chosen serving, your own independent kcal estimate (do NOT copy the candidate), portion certainty and a short reason. Portion reference: 1 roti about 40 g, 1 katori about 150 g, 1 glass about 250 ml..."

Both calls use temperature 0 (ask for the most likely answer, not a creative one) and JSON mode, so identical meals give identical structure.

9.7 Which model, and the switch

  • Live engine: Groq, openai/gpt-oss-120b, chosen after an evaluation: 16.8% median calorie error against 19.4% for llama-3.3-70b and no 400% blow-ups. A reasoning model handles the per-100 g scaling better.
  • Pluggable: LLM_PROVIDER can be groq or openai; models are set by env. Both speak the same OpenAI-compatible API, so only the URL, key and model name differ.
  • Gemini came and went: on 28 October the engine moved to Gemini Flash through Google's compatible endpoint, and the same day went back to Groq: one key, one bill, nearly free, and Gemini is out until the practice set shows it is worth paying for.
  • Beta switch: engine_settings can enable a second provider/model for testers plus a percentage of everyone else. A user's place in the rollout is fixed by their hash, so raising the percentage only adds people. A per-user daily cap (30 uncached runs) protects the budget. Everything fails towards the live engine.

9.8 Health check

The app probes {action: 'health'} on load. It used to report "ok" if a key string merely existed, so an expired key showed as healthy while every parse silently fell back. Now it makes a real one-token call to the provider (cached five minutes) and returns a human-readable reason (401 expired key, 429 quota, 404 retired model). The Log screen says nothing while the engine works and shows one line only when it is offline. The app asks at most once every five minutes, since every Match reports the engine's state anyway.

9.9 The run log and corrections

Every parse writes an engine_runs row: the text, each stage's output, token counts and milliseconds per stage, the final result, whether it was cached or degraded. When the user edits a portion or swaps a food before logging, the app fires {action: 'correction'} with what was actually logged, keyed to the run id. The user appears as sha256(ENGINE_LOG_SALT + user id): a one-way fingerprint that cannot be turned back into a name or email, and changing the salt unlinks all old runs. The first recorded real meal ("100 gm paneer cooked with quarter tablespoon of ghee") found two bugs on day one.

9.10 Security of the function

  • Deployed with --no-verify-jwt so the function can answer the browser's CORS preflight, but every real request is checked: the bearer token is sent to Supabase Auth and must resolve to a user. A token Auth accepted is remembered on that instance for up to five minutes (never past its own expiry), because one meal makes up to three calls with it; the trade-off is that a token revoked by signing out can still reach the engine for those few minutes. A rejected token is never remembered.
  • Allowed origins: https://app.getgrain.fit, the old deficit-cyan.vercel.app, and localhost. A new domain must be added in index.ts and redeployed.
  • Inputs are bounded: audio at most 4 MB of base64, roast text at most 300 characters and 15 items, corrections at most 30 items.

9.11 When the engine is unreachable: the offline parser

If Supabase is not configured, or the function errors, RemoteFoodProvider falls back to LocalFoodProvider: a heuristic in the phone. It splits the text on commas, "and", "+", line breaks and full stops (never a decimal point), pulls a leading number or number word ("two", "half"), strips unit words (katori, bowl, tbsp...), and ranks the curated Indian table with a simple score: exact name or alias 100, starts with 80, contains 60, token overlap 20 plus 10 per token. A stated weight is only scaled against a serving that states its weight in the same unit; otherwise it stays one serving and is flagged. The local table never claims high confidence: a strong hit is medium, a loose one is low. Type-ahead Search always uses this local table, because it must be instant.

9.12 Swapping a match

Each parsed item carries its other candidates. Tapping one calls swapParsedItem. The quantity only transfers when the new serving string is identical; otherwise it resets to 1 and confidence drops to medium with a reason, because carrying "1.5 katori" onto a "100 g raw" row once logged triple the real intake under a high badge. The replaced food stays in the list so a swap is never a dead end.

10.1 Raw versus cooked, done in code

IFCT has no cooked foods. People eat rice and dal cooked, and 100 g of cooked rice is about 33 g raw. If a raw row reached the judge unconverted, it would be read as 100 g eaten: a three-times overcount on the most-logged foods there are. So ifct.ts carries a short, auditable table of yields and offers staples twice:

cooked kcal per 100 g = raw kcal per 100 g / yield
rice (A013, A014, A015): yield 3.0     -> 356 kcal raw becomes 119 cooked
dals (chana, urad, moong, masoor, toor, rajmah): 2.5
wheat vermicelli (A023, A024): 2.2

Cross-check: 119 against USDA cooked white rice at 130 and the curated row at 133. Within 10%, deliberately on the low side because the raw figure carries no cooking fat. Both readings are offered ("100g cooked" first, "100g raw (uncooked weight)" second) and the judge picks the one matching how the portion was described. Eggs are detected as already cooked from their names (boiled, omlet).

A few hand aliases map vernacular to botanical English (toor dal to Red gram; chawal, poha, suji, atta). Six rows start with "Rice" and tied, so plain rice did not make the top three until an exact alias settled it.

11. Voice notes

  1. The phone records with the browser's MediaRecorder in whatever format it likes (Chrome webm, Safari mp4). Maximum 60 seconds.
  2. voice.ts decodes it and resamples to 16 kHz mono WAV (22.05 kHz on old Safari). Speech models work at 16 kHz internally so nothing is lost; a 30-second note stays under 1 MB; and WAV is the one format every speech model reads.
  3. It is sent as base64 to {action: 'transcribe'}. The function forwards it to Whisper large v3 on Groq with language English and a prompt that is a sample meal: "do roti, ek katori dal, 200g chicken breast, 1 tablespoon ghee, paneer bhurji, besan chilla, 1 scoop whey". That steers Whisper to Roman-script Hinglish and the usual spellings, because a general speech model otherwise hears Hindi food words as English ones.
  4. The text lands in the box to check before matching. Nothing is logged from voice alone.

Cost: Whisper on Groq is $0.111 per hour of audio billed at a minimum of 10 seconds, about 3 paise a note. Gemini transcription was tried first and dropped the same day, with Groq Whisper kept as the single path.

12. GrainAI, the roast

Every described meal gets one brutal line after the numbers appear. It is the app's personality, on by default, with a quiet switch on Profile. Mechanics:

  1. The verdict is computed in code first (verdict()): under eating if it is late (8 pm to 4 am) and the day is under half the target; disaster if the meal is 900 kcal or more, or pushes the day over target, or is 400 kcal or more with under 12% of energy from protein; clean if 30% or more of energy is protein; otherwise sloppy.
  2. The facts are worked out in code and written as a short note, not JSON (JSON in pulls formal language out): the meal, its kcal and protein, the time, the verdict, calories left or over, protein still needed.
  3. The model is Qwen 3.8 27B on Groq at temperature 1, with a system prompt that describes a person ("the most savage friend in the group chat"), bans soft AI phrases ("bold", "interesting choice", "keep it up"), allows swearing, and shows ten example roasts it must not reuse. gpt-oss was tried and reads every number back like a bank statement.
  4. Three candidates come back. parseCandidates strips numbering, quotes and every kind of hyphen. pickRoast drops anything matching the banned list, prefers lines without bot tells (fewer than three numbers, under 130 characters, no "ah" or exclamation marks), and picks at random among the survivors. If nothing survives, no roast is shown.
The line it never crossesNothing about the body, weight, looks, abs or belly. Nothing sexual. Nothing about eating disorders, starving, skipping meals, self harm, depression, illness or dying. No religion, caste, race, gender, sexuality or disability. It never guesses gender ("your ex", never "bro" or "girlfriend"). It never tells anyone to eat less than their target. The reason is the audience: athletes and models are exactly the people most at risk from food and body shame, and a tracker that mocks someone for logging a brownie teaches them to stop logging it. A request to roast the belly and the sex life was declined on this basis. The prompt says all this and a word filter on the server enforces it; against the 64 lines from testing, the filter dropped every one that crossed.

No fallback to gpt-oss when Qwen is busy: Groq rate limits are per model, and a roast must never use up the capacity meal matching needs.

13. The maths: targets, budget, adaptive maintenance, predictions

None of this touches AI. Same input, same output, every time.

13.1 From profile to daily target (targets.ts)

BMR (Mifflin-St Jeor) = 10 × weight(kg) + 6.25 × height(cm) − 5 × age  (+5 men, −161 women)
Maintenance (TDEE)    = BMR × activity factor
                        sedentary 1.2, light 1.375, moderate 1.55, active 1.725, very active 1.9
Loss rate             = chosen kg/week, clamped between 0.25 and 1.0
Daily deficit         = rate × 7,700 / 7            (7,700 kcal is about 1 kg of fat)
Target                = maintenance − deficit
Floor                 = max(BMR, 1,200): the target never goes below it
                        (if even the floor exceeds maintenance, eat at maintenance)
Protein               = 1.8 g per kg bodyweight (or the user's manual number)
Fat                   = 0.8 g per kg
Carbs                 = whatever calories remain, never negative

Example: 28-year-old man, 178 cm, 85 kg, moderate, 0.5 kg a week. BMR 1,818; maintenance 2,818; deficit 550; target 2,268; protein 153 g; fat 68 g; carbs 261 g. When the floor bites, a note says "We've set a safer pace. Aggressive deficits backfire and erode muscle."

13.2 Left to eat (budget.ts)

remaining = target + credited exercise − consumed. Exercise credit has a configurable "eat back" factor because eating back 100% of a fuzzy tracker estimate stalls fat loss; today the Log screen passes 0 burned, so the budget is simply target minus eaten. The gauge fraction is consumed over target clamped to 0 to 1; "Over by" replaces "Left to eat" when negative.

13.3 Learning your real maintenance (adaptive-tdee.ts)

The formula above is a textbook guess. Your body is the real experiment. If you ate 2,300 a day for two weeks and lost 0.5 kg, your real maintenance must have been about 2,300 + 0.5 × 7,700 / 14 = 2,575.

weight trend (kg/day) = least-squares slope through the weigh-ins   (robust to water-weight noise)
estimated TDEE        = average logged intake − slope × 7,700
recommended target    = max(floor, estimated TDEE − your chosen daily deficit)

It refuses to guess until there is enough data: at least 7 logged days, 3 weigh-ins spanning 7 days, and coverage of at least 70% of the days between the first and last weigh-in. Coverage matters because the scale keeps counting through a holiday but the intake average does not; ten unlogged days of eating out would show up as weight gained on the logged intake and read as a slow metabolism. Confidence grows with data: low, medium (10 days, 5 weigh-ins, 10-day span), high (14 days, 8 weigh-ins, 14-day span). Today's partial intake is excluded, and unfinished days are blanked first (chapter 14).

13.4 The weekly forecast (weekly-prediction.ts)

The window is the seven days ending yesterday, because a half-eaten today looks like a huge deficit and would swing the number all morning. Average (maintenance − intake) over logged days, times 7, divided by 7,700 gives "on pace to lose 0.42 kg this week". Fewer than 5 logged days shows "building" instead of a number; zero shows "fresh". Missing one or two days are implicitly filled with the logged-day average, which is what average × 7 does.

13.5 The shareable week (week-report.ts, week-card.ts)

Deficit over the last seven full days, days logged, days protein was hit, average kcal against target, weight change. Drawn on a canvas at 1080 × 1350 (Instagram portrait) in the app's own fonts, with getgrain.fit at the bottom; the preview is the exact file shared. On phones the share sheet opens to Instagram or WhatsApp; desktops download. This is the marketing loop for an audience that already posts its progress.

14. Honest history: full days, breaks, fresh starts

This is a product rule as much as a calculation, and it runs everywhere food is summed.

A day is...WhenEffect
countedSomething logged and at least half the calorie target, or the user confirmed it was really everything (a fast, a sick day) from the calendar.In every total and average.
unfinishedLogged, but under half the target and not confirmed. Almost always breakfast logged, the rest forgotten.Held out until finished or confirmed. Would otherwise read as a 2,000 kcal deficit.
missingNothing logged.Unknown. Adds nothing as deficit or surplus. Nothing is ever guessed to fill it.
  • Today is open, so it never counts against a streak in the morning; the streak starts from yesterday if today is not full yet.
  • A break is three or more days in a row without a full day, after the person has logged at least one full day (the days before someone ever logged are not a lapse).
  • Away: while a break is running, History says so plainly: last full day, days since, and that the numbers start again from the next full day.
  • Restart: for 14 days after coming back, History leads with a fresh start that names the break with its dates and counts from the return, with 30, 90 and Year a tap away. No cheering, no guilt.
  • Total deficit maintained = sum over counted days of (maintenance − intake), and estimated fat = that / 7,700. Targets are not versioned per day, so the current maintenance is the reference line; a fair approximation for a journey view.
WhyBefore this, a fortnight off looked like a fortnight of discipline, and a lone breakfast looked like a 2,000 kcal deficit. A person cannot lie to themselves, so a flattering number that is not true is worse than no number. The same dayStatus() function now feeds the weekly card, the Home prediction, Train progress food averages, the adaptive maintenance estimate and the summary a coach sees.

15. Training: logger, set maths, records, offline sync

15.1 The exercise library and name matching

104 exercises, each with a muscle, equipment, kind (weighted or bodyweight) and aliases, ordered roughly by how common they are so ties go to the common one. Matching is built for gym shorthand: names and queries are normalised the same way (lowercase, equipment words shortened: dumbbell to db, barbell to bb; plurals folded; filler dropped; spaces removed), then scored 0 to 100: exact 100; every query word starts a candidate word 72 minus 3 per extra word; prefix 66; substring 56; small typos by edit distance (with neighbour swaps counting as one) 40 to 50. Below 30 is no match. "rdl", "ohp", "db bench", "bss", "skullcrushers" and "pullups" all land. Anything missing becomes a custom exercise in two taps.

15.2 The set maths (workout.ts)

Estimated one rep max (Epley): e1rm = kg × (1 + reps / 30), for 1 to 15 reps (1 rep = the lift itself)
Load of a set               = kg, or for bodyweight moves: bodyweight + added kg
Set score                   = e1rm of the load   (how records are judged)
Hard set                    = ticked, not a warmup, with reps
Volume                      = kg × reps over hard sets (warmups move none)
Record                      = a hard set whose score beats every earlier score by more than 0.05,
                              history first, then earlier sets today; a first ever session sets none

Bodyweight lifts count bodyweight plus added load, so 10 pull ups at 80 kg compare fairly with 6 pull ups carrying 10 kg.

15.3 The logger's one-tap sets

  • Each exercise is a card of sets: set label (W, D, F or the working number), previous, kg, reps, tick.
  • Placeholders are last time's matching set (warmups against warmups, working against working, in order), else the nearest set above it today, else the last set from last time. So a set done the same as last time is one tap on the tick.
  • Tapping a previous set copies it in. A set's number opens its type (warmup, drop, failure) and optional RPE (6 to 10).
  • Every tick starts a rest timer whose length is remembered per exercise (default 90 s); the screen stays awake and the phone buzzes at the end.
  • Finishing names the session from what was trained (60% or more of hard sets in one group gives Push, Pull, Legs or Core; under 20% legs gives Upper body; else Full body) unless the user named it, offers to tick sets with numbers but no tick, lists the records, and can save the layout as a routine.

15.4 Gyms are basements: the offline design (train/store.ts)

  • The workout in progress is saved to the device on every tap and to the account when possible; on load the newer of the two copies wins. Clearing it on the device while offline writes a "cleared at" marker so a stale synced copy is ignored and removed later.
  • Finished workouts go into an outbox as operations (put or delete). The outbox is flushed oldest first and stops at the first failure, so order is preserved. History shows outbox items immediately, overlaid on the synced list.
  • Imports write one month at a time, index first, and need the network; running the same import twice updates rather than doubles because ids are stable.
  • Custom exercises are merged from both copies; one made offline goes up the next time the account answers.

16. Describe a workout and import history (no AI)

describe.ts reads a workout typed or spoken in plain words. It is plain code on the phone: instant, free, and the same words always read the same way. Whatever it cannot place is handed back so the screen asks instead of guessing.

bench 80x8, 80x8, 85x6          squat 100kg 5x5          ohp 50 for 8, 8 and 7
lat pulldown 3 sets of 12 at 60  pull ups bw x 10, +10 x 6
"squats five sets of five at a hundred kilos"   (number words become digits; pounds become kg)

How: normalise (× to x, "body weight" to bw, kilos to kg, pounds to lb, number words to digits, "80 and a half" to 80.5); split into pieces on lines, sentences, commas and "then"; strip leading filler ("and then I did"); move a trailing "on rows" to the front; split each piece into a name and its numbers at the first digit; carry the weight across clauses so "80x8, 8, 7" means three sets at 80; and read patterns such as weight × reps × sets, sets × reps at weight, reps for sets, and "+10" as added load on a bodyweight move. Up to 20 sets per clause. Exercise names go through the library matcher.

importer.ts reads a Strong export, a Hevy export, any training spreadsheet saved as CSV, or pasted notes ("Mon 3 Nov: bench 80x8, 85x6"). Names are matched to the library (Strong's "Incline Bench Press (Dumbbell)" becomes Incline dumbbell press); unknowns are listed first with a muscle guessed, to keep, rename or leave out. Rest timers and timed or distance rows are left out and counted.

17. Progress, and the one line only Grain can write

progress.ts compares a Monday-to-Sunday week or a calendar month with the one before. A week still running is compared with the same days last week, so a Monday is not judged against a whole week. It reports volume and hard sets, hard sets per muscle against a 10-sets-a-week mark, food averages over full days against targets, bodyweight change (against the last weigh-in before the period, else the first in it), and each lift's best estimated max with its change against the previous period (or the last session before, after a break).

Records per exercise: best estimated max, heaviest set, most reps, best session volume, and rep maxes for 1, 2, 3, 5, 8, 10 and 12 reps where a rep count only earns a line if it beats every higher count (95 × 8 already says 95 kg for 5, 3, 2 and 1).

The one line (periodRead) joins the three streams in priority order:

  1. Bodyweight down 0.2 kg or more and median lift change up 2% or more: "Lifts up 3.0% while bodyweight fell 0.6 kg."
  2. Bodyweight down and lifts within half a percent: "Strength held while bodyweight fell 0.6 kg."
  3. Lifts down 2% or more, at least half the days logged, and average kcal under 85% of target: "Lifts slipped 2.4% on 1,850 kcal a day, 18% under target."
  4. Protein averaging under 80% of target over 3 or more full days: "Protein averaged 110 g a day, short of your 150 g target."
  5. Then: lifts up, more hard sets than before, lifts holding, or a plain count.

Only an app holding food, training and the scale together can write lines 1 to 4. That is the reason to switch from three single-purpose apps.

18. Programs, meal plans and coaches

  • Writing: named days with exercises, sets (1 to 10) and rep ranges (1 to 50), how many weeks (1 to 52), and optionally a meal plan with daily calories, protein and named meals. Publishing gives a six-character code (no O, 0, I or 1) and a link.
  • Following: one program at a time. Today's day sits on top of Train with one tap to start; the logger shows each exercise's rep target. The next day is always the one after the last program day done, so a missed session shifts the plan instead of being skipped. Week = workouts done ÷ days per week, plus one. Plan meals appear on the Log screen and log in one tap.
  • The device copy: the followed program is cached on the phone so Train shows today's day instantly and offline.
  • Sharing with the coach (adherence.ts): off until ticked, reversible, and turning it off deletes the summary. The summary covers the last 28 days ending yesterday (or since the follow started): program workouts done against planned (days per week scaled to the window), last workout date, full food days, average kcal and protein, latest weight and change. Never meals, sets or notes. It is refreshed at most every six hours. The coach's screen validates the shape of anything it receives and shows nothing rather than breaking on bad data.

19. Consent, privacy, export and delete

  • Consent before anything else, three separate taps with nothing pre-ticked: 18 or older, terms and privacy policy, health data used for targets. Each agreement is an uneditable row with a version (CONSENT_VERSION = '2026-11-09'); raising the version asks everyone again.
  • Agreeing never waits on the network. The first version blocked every new sign in when the table did not exist yet. Now the person has agreed the moment they tick, the app opens, and if the row cannot be stored it waits on the device and is sent on a later launch.
  • Download my data: every user_kv row (parsed), consents, programs written, and follows, as one JSON file.
  • Delete my account: one database function removes the auth user and everything cascades. Device keys for that account are cleared.
  • What the engine keeps about a person: only a salted hash. Meal text is kept to improve the engine, as the sign in screen says. The landing site has a privacy policy and terms.

20. The back office: access, premium, CRM, stats

  • Access model: one subscription for everyone, price not set. The paywall switch stays off until payments exist; off means everyone gets every feature. hasPremium = !paywall || premiumActive. Admins gift premium by hand with no end date or for 3, 6 or 12 months; a gift shows on that person's Profile as "Premium, a gift from Grain". Nobody can gift themselves.
  • Users: the list with activity counts and gifts.
  • Stats: the numbers in chapter 8.4, refreshed every minute.
  • Creators CRM: on a laptop (1024 px or wider) a full workspace: a strip of what needs you today (follow ups due, overdue, replied with nothing planned, reply rate, roster reach), saved views (needs action, all, roster, prospects, declined), a dense table sorted by urgency (most overdue first, then due today, then replies waiting), inline stage and follow-up edits, bulk moves, CSV export, a side panel with timeline and growth, a pipeline board with drag to move, and keyboard shortcuts (J/K move, Enter open, 1 to 7 set stage, T/W follow up tomorrow or in a week, N new, X select, slash search). 24. Known weaknesses and the engine roadmap

24.1 Where the engine is weak today (from the lab's review of 38 items)

  • The name search is naive: "big" matched "Betel leaves, big" for a Big Mac; chicken biryani ranks ahead of chicken breast for "chicken breast".
  • Cups and spoons are still turned into grams by the model's memory in stage 1. Code should do it from a weight per household measure for each food, the way FNDDS and Nutritionix do.
  • A stated weight is ignored when the matched food is a home serving such as "1 katori (150g)"; only per-100 g rows get the arithmetic.
  • Confidence has not been validated against truth.
  • The practice set is small (27 of 30 weighed meals passing could mean 74% to 97%), and 27 reference rows still need checking against a source or a label.
  • Brands are out of scope: whey, soya chunks, low-fat paneer and protein bars each have one standard row with a note that brands vary. A future "scan a label" feature is the intended answer.
  • The curated table calls itself a stub in its header; its values are reasonable home-portion estimates, which is why the engine prefers it only for dishes and never lets it claim high confidence offline.

24.2 The plan that is on record

  1. Practice set: 81 meals (53 Indian, 28 global), typed as people type them, with reference answers computed from source rows (USDA ids, IFCT codes, pack labels), never typed in. Targets: weighed meals within 5%, dishes within 15%, never off by 2× or more, lower median error than ChatGPT on calories and on protein, answer under 9 seconds.
  2. Scorer: runs the live engine code, resumes partial runs (a full run exceeds a free day of Groq tokens), prints each failure's trace, and reports pass rates with 95% intervals and signed error.
  3. Own food database in Supabase replacing live USDA calls: USDA as the backbone (FNDDS has thousands of dishes as eaten with real portion weights), IFCT for Indian ingredients, chains looked up from their published numbers, the user's country deciding defaults ("milk" is toned in India and 2% in the US). Open Food Facts for packaged food only once its share-alike licence is settled.
  4. Bake-off of stronger models on the set, then pay only if one clearly wins.
  5. Ship through the beta switch, watching corrections.

24.3 App-side things worth knowing

  • Route-level code splitting (Expo's async routes) would cut the first download by another 67 KB, but on SDK 56 it leaves every screen blank. Expo calls it stable on the web from SDK 58, so it comes with an SDK upgrade. The Supabase client also carries about 90 KB of realtime and storage code Grain never uses; removing it means replacing the client and retesting Google sign-in.
  • The adaptive estimate uses the current maintenance as the reference for all past days; targets are not versioned.
  • No native build exists yet; on native the storage would need an AsyncStorage adapter (a comment in kv.ts marks the spot).
  • IFCT licence, SMTP (if email ever returns), and Google Search Console verification are the open operational items.
